# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Afrodite CRM — a mobile-first PWA (React 18 + Vite 5 + Material UI 6) for biomedical/aesthetic clinics, deployed to Firebase Hosting (project `afrodite-62a56`). The UI copy, route paths, comments, and error messages are in **Brazilian Portuguese**; keep new code consistent with that.

## Commands

```bash
npm install
npm run emulators # terminal 1: Auth + Firestore + Storage + Functions emulators (needs firebase-tools + Java); UI at http://127.0.0.1:4000
npm run seed      # once (or to reset): wipes and reloads demo data into the emulators
npm run dev       # terminal 2: Vite dev server on http://localhost:5173 (talks to the emulators)
npm run build     # production build to dist/
npm run preview   # serve the built dist/
npm run deploy    # build + firebase deploy --only hosting,firestore,storage,functions (needs `firebase login`, .env.production, Blaze plan)
```

There is no linter, formatter, or test suite configured. Cloud Functions live in `functions/` (own `package.json`; run `npm install` there once).

Local login (seeded into the Auth emulator): `admin@afrodite.com` / `123456`.

## Architecture

- **Routing** (`src/App.jsx`): uses `HashRouter` (URLs look like `/#/pacientes/p1`). Every authenticated screen is wrapped in `PrivateRoute`, which redirects to `/login` when `useAuth().user` is null. New screens must be registered here.
- **Firebase** (`src/services/firebase.js`): initializes Auth + Firestore + Storage from `VITE_FIREBASE_*` env vars (`VITE_FIREBASE_VAPID_KEY` for web push). `.env.development` sets `VITE_USE_FIREBASE_EMULATORS=true` and project `demo-afrodite` (the `demo-` prefix guarantees no real project is touched). Production config goes in `.env.production` (template: `.env.example`).
- **Auth** (`src/context/AuthContext.jsx`): driven by `afroditeApi.onAuthChange` (Firebase `onAuthStateChanged`). `user === undefined` while the session restores → `initializing`, and `AppRoutes` shows `FullScreenLoader` until then. "Manter conectada" on login chooses local vs. session persistence. Profile (`name`, `role`) lives in `users/{uid}`. Sign-up (`/criar-conta`, `afroditeApi.register`) creates the Auth user + `users/{uid}` with role `convidado`; `/esqueci-senha` uses `requestPasswordReset` (always shows the same confirmation, so it doesn't reveal which emails exist). Both share `AuthLayout` + `PasswordField` with the login screen.
- **Data layer** (`src/services/afroditeApi.js`): the single data boundary — screens import only `* as afroditeApi`, never Firebase directly. Return shapes are what screens consume: calendar dates are stored as `'YYYY-MM-DD'` strings (local time, helpers in `services/dates.js`) and returned formatted `DD/MM/YYYY` (raw value kept in `dateKey` / `*Date`); instants (`leads.createdAt`, messages) are Timestamps. Derived numbers (dashboard, finance summary, commission values, durations) are computed here, not stored. `getAgendaDayTabs` is the one synchronous function. Errors without `code` are already Portuguese; Firebase errors are translated by `utils/errors.js#friendlyMessage`.
- **Firestore model**: `users` (+ `notifications`, `devices` = FCM tokens), `patients` (+ subcollections `anamnese/main`, `procedures`, `photos`, `prescriptions`, `documents`), `appointments` (denormalized patient name/age/CPF, `status` Agendado → Em atendimento → Concluído, `reminderSent`), `leads` (+ `messages`), `payments` (launches = paid payments), `commissions`. Records created in the app carry `createdBy` (uid) so the creator isn't notified. `createAppointment` rejects room/time overlaps and updates the patient's `nextReturn`.
- **CRM** (leads ↔ patients): lead stages are `PIPELINE_STAGES` (Novo → Em contato → Qualificado → Proposta) plus outcomes `Convertido` / `Perdido` (`lostReason` from `LOST_REASONS`). `Convertido` is only reachable through `convertLeadToPatient`, which creates the patient (`leadId`, `source`, `interest`) and sets `lead.patientId`. Leads have `nextFollowUp` (dateKey; `toLead` derives `followUpState` overdue/today/upcoming + `followUpLabel`); new leads default to today. Relationship history lives in `leads/{id}/activities` and `patients/{id}/activities` (`type`: ligacao/whatsapp/visita/email/nota/status/criado/conversao/perdido/followup/proposta, `createdByName`) — write them in the same `writeBatch` as the change they describe. `logContact` moves a `Novo` lead to `Em contato` (sending a WhatsApp message does too). `getPatientTimeline` merges patient activities, the origin lead's activities, appointments and procedures. `findContactsByPhone` powers the duplicate warning on create/convert. Leads screen: list/board toggle (`?visao=funil`), filters in `?filtro=`.
- **Routing detail**: private routes are wrapped in `KeyedByParams`, which remounts the screen when `:id` changes (lead → lead via a notification), so tabs/sheets/data never carry over.
- **Storage** (`storage.rules`): `patients/{id}/photos/*` (images < 15 MB; resized to ≤ 2048px JPEG in the browser) and `patients/{id}/documents/{docId}/*` (PDF/images < 20 MB). Firestore docs keep `storagePath` + `url` (download URL — anyone with the link can open it).
- **Notifications**: Cloud Functions (`functions/index.js`, region `us-central1` to match the `nam5` database) write to `users/{uid}/notifications` for every staff user except the actor, then send FCM push to `users/{uid}/devices`: new lead, new appointment, message received from a lead, and a scheduled job every 5 min (`reminders.js`, America/Sao_Paulo) for appointments starting within 30 min, plus, from 08:00, leads whose `nextFollowUp` is today (`followUpNotified` prevents repeats). Seeded docs have `_seed: true` and are ignored by triggers. Client: `NotificationsProvider` (`src/context/NotificationsContext.jsx`) keeps one `onSnapshot` subscription; `NotificationBell` sits in tab-root headers; `/notificacoes` lists them and toggles push (`public/firebase-messaging-sw.js`, config passed by query string, scope `/firebase-cloud-messaging-push-scope`). Logout unregisters the device token. Push is disabled with emulators. Rules (`firestore.rules`): `users/{uid}` is writable only by its owner, created only with role `convidado`, and the role can't be changed from the client (set higher roles via the console); every other collection is read/write for any signed-in user — since sign-up is open, tighten by role before real patient data. Seed data lives in `scripts/seed.mjs` (dates relative to today).
- **Screen pattern**: fetch with `useAsync(() => afroditeApi.x(id), [id])` (`src/hooks/useAsync.js`) → `{ data, error, loading, reload, setData }`; it ignores stale responses. Render `ListSkeleton`/`Skeleton` while loading, `ErrorState` (with retry) on error, `EmptyState` when empty. After a write, update locally with `setData` and confirm with `useToast()` (`src/context/ToastContext.jsx`). There is no global data store.
- **Layout & design system**: wrap screens in `AppScreen` (`header`, `nav` → renders the floating `BottomNav` and the bottom padding for it; `fab` → `{ label, icon, onClick }` floating button; content max-width 560). Never put `position: fixed` elements inside the screen content: its entrance animation uses `transform`, which makes fixed children position relative to the content instead of the viewport — use the `fab` prop. The Agenda keeps the selected day in the URL (`/agenda?dia=YYYY-MM-DD`), shows a 14-day strip with dots from `getAppointmentCountsByDay`, and has a native date picker for any other date. Headers use `ScreenHeader` (`large` serif title for tab roots; `back` for nested) or `PatientHeader`. Shared pieces in `src/components/`: `ListCard`, `StatusChip` (tones mapped in `theme/status.js` — add new statuses there), `PersonAvatar`, `PillTabs` (filters), `SectionTabs` (profile sections), `MetricCard`, `InsightCard`, `SectionTitle`, `InfoField`, `BottomSheet` (forms/actions), `StateViews`. Formatting helpers in `utils/format.js` (currency, initials, masks). `BottomNav` matches tabs by path prefix; `/financeiro` highlights "Mais".
- **Theme** (`src/theme/theme.js`): MUI theme + `brand` colors (wine `#6a3b4f`, rose, blush, gold, cream, ink, muted, line), `gradients`, `shadows`, `fonts`. Typography: Cormorant Garamond (h1–h5, display titles) + Inter Variable (body), self-hosted via `@fontsource` in `main.jsx`. Most card/button/input styling comes from theme overrides — prefer them over per-screen `sx`. Use `env(safe-area-inset-*)` for top/bottom spacing. The PWA manifest colors in `vite.config.js` mirror `brand.wine`.
- **Feature folders**: `src/screens/patients/` (list + `partials/NewPatientSheet`, profile with tabs, editable anamnese, prescriptions + `NewPrescriptionSheet`, documents + `DocumentUploadSheet`, photo gallery + `PhotoUploadSheet`), `src/screens/agenda/NewAppointmentSheet.jsx` (used by Agenda FAB and patient profile) and `src/screens/leads/` (list + `NewLeadSheet`, detail with funnel, WhatsApp chat that persists messages). Actions not built yet show an "em breve" toast.

## PWA / Hosting

- `vite-plugin-pwa` with `registerType: 'autoUpdate'`; FCM uses its own service worker (`public/firebase-messaging-sw.js`, also `no-cache` in `firebase.json`); icons live in `public/icons/`. Fonts (`woff2`) are precached. Vendor code is split into `react`, `mui`, `firebase` chunks (`build.rollupOptions.output.manualChunks`).
- `firebase.json` serves `dist/`, rewrites all paths to `/index.html`, and sets `Cache-Control: no-cache` on `/sw.js` so service-worker updates propagate.
